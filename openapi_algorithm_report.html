Bảng 3.12 - Quy trình tổng quan áp dụng giải thuật tự sinh test case vào hệ thống
Cơ sở lý thuyết giải thuật Áp dụng phương pháp tự động sinh ca kiểm thử theo tiếp cận đặc tả (Specification-based approach) từ nghiên cứu khoa học: "Automatic Generation of Test Cases for REST APIs: a Specification-Based Approach" (tác giả Hamza Ed-douibi, Javier Luis Canovas Izquierdo, Jordi Cabot). Giải thuật chuyển đổi đặc tả OpenAPI (Swagger) thành mô hình kiểm thử độc lập, tự động suy diễn dữ liệu đúng (Nominal) và dữ liệu lỗi (Faulty) để kiểm thử toàn diện các endpoint dịch vụ.
Quy trình 4 bước của giải thuật 1. Model Extraction (Trích xuất đặc tả): Bộ quét mã nguồn đọc các comment cú pháp @openapi trong các file Controller của ứng dụng Node.js/Express, sử dụng thư viện swagger-jsdoc để tự động kết xuất ra đặc tả OpenAPI trung gian định dạng YAML độc lập dưới thư mục server/generated-openapi/.
2. Model Extension (Suy diễn và làm giàu dữ liệu): Sử dụng bộ suy diễn dữ liệu để sinh các bộ tham số hợp lệ (Nominal) và dữ liệu lỗi có chủ đích (Faulty) dựa trên kiểu dữ liệu và ràng buộc của JSON Schema trong đặc tả, điền vào mô hình kiểm thử.
3. Model Transformation (Biến đổi mô hình kiểm thử): Chuyển đổi các đặc tả API và các bộ dữ liệu đầu vào tương ứng thành một cấu trúc TestSuite trung gian độc lập chứa đầy đủ thông tin HTTP request và các mệnh đề khẳng định kiểm chứng kết quả (Assertions) như mã lỗi HTTP trả về, sự tồn tại của header hay định dạng JSON response body.
4. Code Generation (Sinh mã nguồn kiểm thử thực tế): Trực tiếp biên dịch cấu trúc TestSuite thành tệp mã nguồn kiểm thử bằng ngôn ngữ Javascript sử dụng framework Jest và thư viện Supertest, lưu trữ dưới thư mục server/generated-tests/openapi-generated/. Các tệp này có thể thực thi trực tiếp trên server qua lệnh npm run test:openapi-generated.
Triển khai cấu trúc thư mục & mã nguồn thực tế - swaggerDef.js: Quét comment OpenAPI trong controllers, xuất file openapi.yaml toàn hệ thống và YAML riêng cho từng controller tại generated-openapi/*.yaml.
- test-generator/paramInferrer.js: Bộ suy diễn tham số, đảm nhiệm sinh dữ liệu Nominal hợp lệ theo luật PR1, PR2 của bài báo.
- test-generator/faultGenerator.js: Bộ sinh dữ liệu lỗi có chủ đích theo luật GR2 (F1-F5) của bài báo.
- test-generator/testSuiteGenerator.js: Biến đổi các operation trong spec thành danh sách các ca kiểm thử chứa Assertion đầu vào/đầu ra phù hợp.
- test-generator/codeGen.js: Ghi và định dạng danh sách ca kiểm thử thành tệp code Jest hoàn chỉnh.
- test-generator/generatedTestEnvironment.js: Thiết lập môi trường Mock cô lập cho database, repository layer và middleware xác thực để đảm bảo các ca kiểm thử chạy độc lập, ổn định và không làm bẩn/hỏng database thật.
Đặc tính an toàn (Safe vs Unsafe mode) Giải thuật được chạy dưới dạng tự động mock toàn bộ tầng kết nối dữ liệu (Mongoose models/DB connection) qua cơ chế nạp trước tệp generatedTestEnvironment.js. Việc này triệt tiêu hoàn toàn các ảnh hưởng phụ (side-effects) có hại khi chạy các phương thức thay đổi dữ liệu (POST, PUT, DELETE) lên hệ thống cơ sở dữ liệu thật của cửa hàng siêu thị mini.
Bảng 3.13 - Ví dụ 1: Bộ suy diễn giá trị tham số hợp lệ (PR1 & PR2)
Thành phần hiện thực hóa Bộ suy diễn tham số đầu vào hợp lệ: paramInferrer.js (nằm trong thư mục server/test-generator/paramInferrer.js).
Quy tắc lý thuyết áp dụng - Quy tắc PR 1 (Simple Parameter Inference): Tự động đọc và ưu tiên sử dụng các thuộc tính có sẵn trong OpenAPI Spec như default, example hoặc phần tử đầu tiên của tập enum.
- Quy tắc PR 2 (Dummy Parameter Inference): Nếu không có sẵn thông tin tĩnh, tự động phán đoán và sinh ngẫu nhiên các dữ liệu giả định hợp lệ dựa trên kiểu dữ liệu (Data Type) kết hợp cơ chế phán đoán heuristics theo tên tham số đầu vào.
Hiện thực hóa chi tiết trong mã nguồn Hàm chính inferValidValue(schema, fieldName) xử lý theo độ ưu tiên như sau:
1. Đọc thuộc tính mặc định: Kiểm tra thuộc tính schema.default. Nếu tồn tại, trả về giá trị này.
2. Trích xuất enum: Kiểm tra nếu là enum (schema.enum) và có phần tử, chọn phần tử đầu tiên schema.enum[0].
3. Heuristic theo tên tham số (FieldName) kết hợp định dạng:
    - Nếu định dạng schema.format === 'email' hoặc tên trường chứa chuỗi email: Sinh chuỗi hợp lệ "test@example.com".
    - Nếu định dạng schema.format === 'date-time' hoặc tên trường kết thúc bằng date, _at: Trả về chuỗi ISO date hợp lệ "2026-01-01T00:00:00.000Z".
    - Nếu tên trường kết thúc bằng hoặc chứa từ khóa id (ví dụ customerId, productId, _id): Hệ thống phán đoán tham số là mã định danh MongoDB ObjectId và trả về chuỗi 24 ký tự hex hợp lệ: "507f1f77bcf86cd799439012".
    - Nếu tên trường là page, limit: Trả về giá trị mặc định của phân trang là số nguyên 1.
    - Nếu tên trường chứa phone: Trả về chuỗi số điện thoại hợp lệ "0901234567".
    - Nếu chứa code: Trả về chuỗi mã ký tự hợp lệ "CODE123".
4. Xử lý kiểu dữ liệu cơ bản của JSON Schema:
    - Kiểu integer: Trả về giá trị tối thiểu schema.minimum nếu có, ngược lại trả về 1.
    - Kiểu number: Trả về schema.minimum hoặc số thực 1.0.
    - Kiểu boolean: Trả về giá trị mặc định true.
    - Kiểu string: Trả về chuỗi "test_value" (hoặc lặp lại ký tự để thỏa mãn điều kiện độ dài tối thiểu minLength nếu có).
    - Kiểu array: Trả về một mảng chứa 1 phần tử được sinh đệ quy.
    - Kiểu object: Duyệt đệ quy qua danh sách thuộc tính schema.properties để dựng một object hợp lệ đầy đủ.
Vai trò thực tế Cung cấp dữ liệu đầu vào ổn định và đúng đắn nhất cho các ca kiểm thử Nominal (happy path), đảm bảo yêu cầu HTTP đi qua được các bộ lọc định dạng ở Controller, giúp kiểm thử hành vi xử lý nghiệp vụ chính của API.
Bảng 3.14 - Ví dụ 2: Bộ tự động sinh dữ liệu lỗi (GR2 - F1 đến F5)
Thành phần hiện thực hóa Bộ sinh dữ liệu lỗi có chủ đích: faultGenerator.js (nằm trong thư mục server/test-generator/faultGenerator.js).
Quy tắc lý thuyết áp dụng Quy tắc GR 2 (Faulty Test Case Rules): Tự động sinh dữ liệu vi phạm trực tiếp các ràng buộc kiểu dữ liệu hoặc cấu trúc được đặc tả trong JSON Schema, nhằm kiểm chứng khả năng phòng thủ của hệ thống REST API ở Backend. Bất cứ khi nào Client gửi dữ liệu vi phạm, Backend bắt buộc phải xử lý từ chối và phản hồi bằng một mã lỗi Client (nhóm 4xx), tuyệt đối không được sập server (lỗi 500) hoặc chấp nhận dữ liệu sai (mã 2xx).
Hiện thực hóa chi tiết trong mã nguồn Bộ sinh dữ liệu lỗi chia thành 5 nhóm hàm tương ứng với các luật biến đổi lỗi của bài báo:
1. F1 (Type Violation - Sai kiểu dữ liệu): Hàm generateF1_TypeViolation(schema) đọc kiểu dữ liệu được khai báo và trả về một giá trị cố ý sai kiểu:
    - Khai báo string: trả về giá trị số nguyên 123.
    - Khai báo integer/number/boolean: trả về chuỗi "wrong_type".
    - Khai báo array: trả về một object rỗng {}.
    - Khai báo object: trả về chuỗi "wrong_type".
2. F2 (Boundary Violations - Vi phạm giới hạn biên): Hàm generateF2_BoundaryViolations(schema) sinh dữ liệu vượt ngoài các ngưỡng số hoặc mảng tối đa/tối thiểu:
    - Vi phạm độ dài tối thiểu (minLength): Sinh chuỗi có độ dài bằng minLength - 1.
    - Vi phạm độ dài tối đa (maxLength): Sinh chuỗi có độ dài bằng maxLength + 1.
    - Vi phạm số nhỏ nhất (minimum): Sinh giá trị bằng minimum - 1.
    - Vi phạm số lớn nhất (maximum): Sinh giá trị bằng maximum + 100.
    - Vi phạm số lượng phần tử mảng (minItems): Trả về mảng rỗng [].
3. F3 (Required Missing - Thiếu trường bắt buộc): Hàm generateF3_RequiredMissing(requiredFields) nhận danh sách các trường bắt buộc của schema, tạo ra các trường hợp lỗi bằng cách loại bỏ (delete) lần lượt từng trường bắt buộc khỏi body của request gửi đi.
4. F4 (Format & Pattern Violation - Vi phạm định dạng / Regex): Hàm generateF4_FormatViolation(schema):
    - Nếu format === 'email': Trả về chuỗi phi email là "not-an-email".
    - Nếu format === 'date-time': Trả về chuỗi ngày sai quy chuẩn "not-a-date".
    - Nếu có regex pattern: Trả về giá trị "invalid_value" cố ý không khớp với biểu thức chính quy.
5. F5 (Enum Violation - Vi phạm danh sách Enum): Hàm generateF5_EnumViolation(schema) kiểm tra thuộc tính enum, trả về một chuỗi không bao giờ nằm trong tập hợp enum hợp lệ là "__invalid_enum__".
Vai trò thực tế Tạo ra các ca kiểm thử bảo mật đầu vào (Input Security Testing) tự động, phát hiện ngay các lỗi nghiêm trọng ở Backend như lỗi 500 (gây sập ứng dụng do thiếu try-catch khi dữ liệu null/undefined) hoặc lỗi 200 nhưng chấp nhận dữ liệu rác (do thiếu validator middleware ở route).
Bảng 3.15 - Ví dụ 3: Bộ thiết lập Assertions và Sinh code kiểm thử Jest
Thành phần hiện thực hóa Bộ điều phối biến đổi và sinh mã kiểm thử: testSuiteGenerator.js và codeGen.js (trong thư mục server/test-generator/).
Quy tắc lý thuyết áp dụng - Model Transformation (Biến đổi mô hình): Gom các thông tin tĩnh trong đặc tả OpenAPI thành các ca kiểm thử thuộc TestSuite Model, gán trước mã kết quả mong đợi (Expected Status Code Assertion).
- Code Generation (Sinh mã kiểm thử): Chuyển đổi thông tin TestSuite trừu tượng thành mã nguồn kiểm thử thực tế có thể biên dịch, chạy trực tiếp trên môi trường kiểm thử của Express (Supertest + Jest).
Hiện thực hóa chi tiết trong mã nguồn 1. Tạo danh sách ca kiểm thử trong testSuiteGenerator.js:
    - Hàm generateNominalTests(): Lấy danh sách operations từ spec, sinh dữ liệu body và param hợp lệ, gán thuộc tính expectStatus: [200, 201, 204].
    - Hàm generateFaultTests(): Duyệt qua các operation sửa đổi dữ liệu (POST, PUT, PATCH), đọc schema để sinh dữ liệu lỗi (thiếu trường, sai định dạng, sai enum) và gán thuộc tính kiểm thử mong đợi mã lỗi client: expectStatus: [400, 422].
2. Chuyển đổi thành mã nguồn Jest trong codeGen.js:
    - Duyệt qua mảng các ca test và sinh ra chuỗi mã nguồn dạng hàm test() của Jest:
    - Tự động thêm phần import thư viện supertest và ứng dụng app của Express.
    - Tự động thiết lập header Content-Type: application/json và chèn chuỗi .send() hoặc .query() tương ứng với dữ liệu đầu vào đã được suy diễn.
    - Chèn Assertion cụ thể:
        expect([${test.expectStatus.join(', ')}]).toContain(res.status);
    - Ghi chuỗi mã nguồn hoàn chỉnh thành tệp vật lý [controllerName].test.js lưu vào đĩa tại thư mục generated-tests/openapi-generated/.

Bước 3: Suy diễn và sinh bộ dữ liệu Test (Nominal & Faulty) Bộ sinh testSuiteGenerator.js đọc tệp YAML trên và thực thi giải thuật suy diễn dữ liệu:

A. Sinh ca kiểm thử danh định (Nominal):
- Trường name (kiểu string): suy diễn thành "test_value" (PR2).
- Trường email (kiểu string, format email): suy diễn thành "test@example.com" (PR2).
- Trường phone (kiểu string, chứa "phone"): suy diễn thành "0901234567" (Heuristics PR2).
- Trường status (enum): chọn giá trị enum đầu tiên "active" (PR1).
👉 Dữ liệu Body Nominal gửi đi: { "name": "test_value", "email": "test@example.com", "phone": "0901234567", "status": "active" }.

B. Sinh ca kiểm thử lỗi (Faulty):
- Lỗi F3 (Thiếu trường bắt buộc 'name'): Loại bỏ trường name ra khỏi body.
👉 Dữ liệu gửi: { "email": "test@example.com", "phone": "0901234567", "status": "active" }.
- Lỗi F3 (Thiếu trường bắt buộc 'email'): Loại bỏ trường email ra khỏi body.
👉 Dữ liệu gửi: { "name": "test_value", "phone": "0901234567", "status": "active" }.
- Lỗi F4 (Sai định dạng email): Ghi đè trường email bằng chuỗi sai định dạng.
👉 Dữ liệu gửi: { "name": "test_value", "email": "not-an-email", "phone": "0901234567", "status": "active" }.
- Lỗi F5 (Vi phạm danh sách Enum của status): Ghi đè trường status bằng giá trị ngoài enum.
👉 Dữ liệu gửi: { "name": "test_value", "email": "test@example.com", "phone": "0901234567", "status": "__invalid_enum__" }.
Bước 4: Biên dịch mã nguồn Jest được sinh ra tự động Tệp kiểm thử thực thi được sinh ra tự động và lưu tại [customerController.test.js](file:///c:/mini-supermarket-management/server/generated-tests/openapi-generated/customerController.test.js): 
const request = require('supertest');
require('../../test-generator/generatedTestEnvironment');
const app = require('../../server');

describe("customerController generated API suite", () => {
  // Ca test Nominal - happy path
  test("[NOMINAL] createCustomer - happy path", async () => {
    const res = await request(app)
      .post("/api/customers")
      .set('Content-Type', 'application/json')
      .send({
        "name": "test_value",
        "email": "test@example.com",
        "phone": "0901234567",
        "status": "active"
      });
    expect([200, 201, 204]).toContain(res.status);
  });

  // Ca test Faulty - Thiếu trường 'name' bắt buộc
  test("[FAULT-F3] createCustomer - missing:name", async () => {
    const res = await request(app)
      .post("/api/customers")
      .set('Content-Type', 'application/json')
      .send({
        "email": "test@example.com",
        "phone": "0901234567",
        "status": "active"
      });
    expect([400, 422]).toContain(res.status);
  });

  // Ca test Faulty - Sai định dạng 'email'
  test("[FAULT-F4] createCustomer - format:email on email", async () => {
    const res = await request(app)
      .post("/api/customers")
      .set('Content-Type', 'application/json')
      .send({
        "name": "test_value",
        "email": "not-an-email",
        "phone": "0901234567",
        "status": "active"
      });
    expect([400, 422]).toContain(res.status);
  });

  // Ca test Faulty - Vi phạm enum 'status'
  test("[FAULT-F5] createCustomer - enum on status", async () => {
    const res = await request(app)
      .post("/api/customers")
      .set('Content-Type', 'application/json')
      .send({
        "name": "test_value",
        "email": "test@example.com",
        "phone": "0901234567",
        "status": "__invalid_enum__"
      });
    expect([400, 422]).toContain(res.status);
  });
});
Bước 5: Thực thi và Kiểm chứng (Assertions) Khi chạy lệnh npm run test:openapi-generated, Jest sẽ khởi chạy tệp này:
- Ca test Nominal gửi dữ liệu chuẩn lên API và kiểm tra xem response trả về có nằm trong tập [200, 201, 204] hay không. Nếu có, ca test vượt qua thành công (Passed).
- Các ca test Faulty gửi dữ liệu lỗi lên và kiểm tra xem mã trả về có thuộc [400, 422] hay không. Nếu API xử lý đúng (từ chối và trả về lỗi Client), ca test sẽ Passed. Nếu server bị sập (lỗi 500) hoặc chấp nhận dữ liệu sai (lỗi 200), ca test sẽ báo thất bại (Failed) để nhà phát triển kịp thời sửa chữa lỗ hổng bảo mật.
