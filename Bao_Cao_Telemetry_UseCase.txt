BÁO CÁO PHÂN TÍCH USE CASE, CHẤT LƯỢNG VÀ LUỒNG CODE THỰC THI (CODE FLOW)
KÈM VÍ DỤ CODE THỰC TẾ & CƠ CHẾ HOẠT ĐỘNG CỦA GIAO DIỆN HIỂN THỊ
===========================================================================

Báo cáo này trình bày chi tiết về cách Hệ thống Quản lý Siêu thị Mini áp dụng tiêu chuẩn Giám sát hệ thống (Observability - Telemetry) của các kiến trúc phần mềm hiện đại. Thông qua việc đối chiếu trực tiếp giữa Source Code (Backend) và Giao diện Giám sát (Frontend System Monitor), chúng ta sẽ chứng minh khả năng đáp ứng các Use Case (UC) trọng yếu, giải quyết bài toán Race Condition và đảm bảo hiệu năng.

---------------------------------------------------------------
PHẦN 1: GIẢI MÃ CHI TIẾT CÁC CHỈ SỐ TRÊN GIAO DIỆN SYSTEM MONITOR
---------------------------------------------------------------
Giao diện `SystemMonitor.jsx` không chỉ hiển thị các con số ngẫu nhiên, mà nó trực tiếp parse dữ liệu từ API `/metrics` (Prometheus format) và `/api/telemetry/traces` (OpenTelemetry format). Dưới đây là phân tích chuyên sâu về từng chỉ số:

[A. TAB METRICS] - Giám sát "Sinh hiệu" của Máy chủ & Node.js Runtime:
Do Node.js hoạt động dựa trên kiến trúc Đơn luồng (Single-Threaded) kết hợp Non-blocking I/O, các chỉ số sau quyết định sự sống còn của hệ thống:

1. Memory Usage (RSS - Resident Set Size): 
   - Ý nghĩa: Là tổng dung lượng RAM vật lý mà Hệ điều hành (OS) đang cấp phát cho toàn bộ tiến trình Backend (bao gồm cả code C++ core của Node, V8 engine, và mã JS).
   - Phân tích: Con số này thường dao động từ 100MB - 200MB. Nếu RSS tăng vượt mức giới hạn của Server (ví dụ > 1GB trên server 1GB RAM), hệ điều hành sẽ kích hoạt cơ chế OOM Killer (Out Of Memory) và "giết" ngay lập tức Backend, gây sập toàn hệ thống.

2. Node.js Heap Used:
   - Ý nghĩa: Vùng nhớ dùng để lưu trữ các biến, Object, Array, String... sinh ra trong quá trình chạy nghiệp vụ (ví dụ: giỏ hàng, thông tin user).
   - Phân tích: Nhờ Garbage Collector (Bộ thu gom rác) của V8 Engine, Heap Used sẽ tăng lên khi có request và giảm xuống khi request xử lý xong. NẾU chỉ số này biểu diễn thành một đường thẳng đi lên liên tục mà không bao giờ tụt xuống -> Hệ thống chắc chắn bị lỗi Rò rỉ bộ nhớ (Memory Leak), lập trình viên quên giải phóng biến.

3. Total CPU Time (process_cpu_user_seconds_total):
   - Ý nghĩa: Tổng thời gian vi xử lý (CPU) đã chạy trong chế độ User Mode để tính toán các logic (như mã hóa bcrypt, tính toán giỏ hàng).
   - Phân tích: Giúp đo lường cường độ tính toán của Backend.

4. Event Loop Lag (Cực kỳ quan trọng & Đắt giá nhất):
   - Ý nghĩa: Độ trễ của Vòng lặp Sự kiện (Event Loop). Trong Node.js, mọi request đều xếp hàng trong Event Loop.
   - Phân tích: Mức lý tưởng là < 0.005s. Nếu hệ thống gọi một vòng lặp `for` đồng bộ xử lý 1 triệu dòng data, hoặc mã hóa file nặng, Event Loop sẽ bị "nghẽn". Lúc này Event Loop Lag sẽ tăng vọt > 0.1s. Hậu quả: Dù Server còn dư RAM, dư CPU, nhưng TẤT CẢ người dùng khác truy cập vào web đều bị treo (quay đều) vì Event Loop đang bận xử lý tác vụ của người dùng trước đó.

5. Active Resources & Active Handles:
   - Thể hiện số lượng kết nối mạng (Socket), kết nối Database đang mở. Giúp phát hiện lỗi "quên đóng kết nối DB".

[B. TAB TRACES] - Giám sát Luồng Code & Nghiệp vụ (Waterfall Architecture):
Thay vì đọc Log Console (dạng text trôi tuột, khó tra cứu), hệ thống dùng chuẩn OpenTelemetry để gom nhóm các tác vụ thành "Traces" và "Spans".

1. Cấu trúc Waterfall (Thác nước):
   - Trục hoành là thời gian. Độ dài của thanh màu biểu thị chính xác số mili-giây (ms) mà hàm đó thực thi. Nhìn vào biểu đồ, Developer biết ngay cổ chai (Bottleneck) nằm ở bước nào (ví dụ: query DB chậm hay gọi API bên thứ 3 chậm).
2. Phân loại màu sắc UI:
   - Thanh màu Xanh (Code 0): Giao dịch thành công, HTTP 200.
   - Thanh màu Đỏ (Code 2): Bắt được Exception, HTTP 400/500 (ví dụ: sai mật khẩu, mua lố số lượng tồn kho).
3. Attributes (Khái niệm Business Observability):
   - Cải tiến lớn nhất: Log truyền thống chỉ ghi "POST /order 200 OK". Trace ghi lại "Mã khách hàng", "Tổng tiền", "Số lượng món". Biến màn hình kỹ thuật thành màn hình Báo cáo Kinh doanh thời gian thực.

PHẦN 2: CHỨNG MINH SỰ ĐÁP ỨNG USE CASE QUA TRACES & CODE THỰC TẾ
---------------------------------------------------------------

1. BẢO MẬT & PHÂN QUYỀN (SECURITY) - UC13.1, UC5.1 (LOGIN/AUTH)
---------------------------------------------------------------
* BỐI CẢNH (UC): Đăng nhập là chốt chặn an ninh đầu tiên. Cần lưu vết mọi nỗ lực đăng nhập (kể cả thất bại) để phục vụ Audit (Kiểm toán bảo mật) sau này.

* VÍ DỤ CODE THỰC TẾ (`controllers/authController.js`):
```javascript
// Bọc toàn bộ logic đăng nhập vào một Span có tên 'auth.login'
const { token, account, profile } = await traceLogin(
  username, req.ip, req.headers['user-agent'],
  async () => { return await authService.login(username, password); }
);
```

* TRÊN GIAO DIỆN TELEMETRY UI:
- Tại Tab Traces, mỗi cú click "Đăng nhập" lập tức sinh ra một Trace `auth.login`.
- Attributes ghi nhận rõ: IP của người dùng, Trình duyệt (User-Agent), Tên đăng nhập (`auth.username`), và Quyền (`auth.role`).
- GIÁ TRỊ: Nếu hệ thống bị tấn công Brute Force (thử mật khẩu liên tục), màn hình UI sẽ rực màu Đỏ, kèm theo chi tiết IP kẻ tấn công. Admin có thể block IP đó ngay lập tức.


2. ĐỘ TIN CẬY & TOÀN VẸN DỮ LIỆU (RELIABILITY) - UC21.3 (CHECKOUT)
------------------------------------------------------------------
* BỐI CẢNH (UC): Siêu thị có đợt Flash Sale. Một lon Coca chỉ còn 1 kho, nhưng có 100 khách hàng cùng ấn nút "Thanh toán" tại cùng 1 mili-giây. Nếu code bằng `stock = stock - qty` rồi `save()`, hệ thống sẽ bán ra 100 lon (Bán âm kho - Race Condition).

* VÍ DỤ CODE THỰC TẾ (`controllers/orderController.js`):
```javascript
// 1. Trace quá trình Checkout
await traceCheckout(customer_id, cart_id, async ({ setOrderAttributes }) => {
  
  // 2. GIẢI QUYẾT RACE CONDITION BẰNG ATOMIC UPDATE CỦA MONGODB
  for (const item of cartItems) {
    const qty = item.quantity;
    
    // Lệnh UpdateOne với điều kiện $gte (Lớn hơn hoặc bằng)
    // Cấp phép cho MongoDB tự động khóa (Lock) row này và kiểm tra.
    // Nếu stock thực tế < qty -> Lệnh cập nhật trả về modifiedCount = 0 (Từ chối bán)
    const productUpdate = await Product.updateOne(
      { _id: productId, current_stock: { $gte: qty } },
      { $inc: { current_stock: -qty } }
    );

    if (productUpdate.modifiedCount === 0) {
      throw new Error(`Sản phẩm đã hết hàng!`); // Lập tức văng Exception -> Đơn hàng bị hủy
    }
    // ... Trừ tương tự cho ProductBatch (kho lô hàng)
  }
  
  // Cập nhật giá trị đơn hàng lên UI
  setOrderAttributes({ totalAmount: totalAmount, itemCount: cartItems.length });
});
```

* TRÊN GIAO DIỆN TELEMETRY UI:
- Khi 100 người mua cùng lúc, UI sẽ hiện 1 thanh `order.checkout` màu XANH (Người mua thành công đầu tiên).
- 99 người còn lại sẽ sinh ra 99 thanh màu ĐỎ (Lỗi hết hàng). Trace giúp khẳng định rằng cơ chế khóa DB (Atomic) đã hoạt động hoàn hảo.
- Mở chi tiết thanh màu Xanh, Quản lý thấy ngay: Đơn hàng này đem về Doanh thu bao nhiêu (`order.total_amount`).


3. DỄ BẢO TRÌ & TỐI ƯU HÓA (MANAGEABILITY) - UC14 (PRODUCT SEARCH)
-----------------------------------------------------------------
* BỐI CẢNH (UC): Chức năng tìm kiếm sản phẩm là nơi bị gọi nhiều nhất. Nếu chức năng này chậm, trải nghiệm khách hàng sẽ cực tệ.

* VÍ DỤ CODE THỰC TẾ (`controllers/productController.js`):
```javascript
const dataResponse = await traceProductSearch(req.query, async () => {
  return await productService.getAllProducts(req.query);
});
// Ghi nhận Attributes: Từ khóa khách tìm, số lượng kết quả trả về
```

* TRÊN GIAO DIỆN TELEMETRY UI:
- Trace xuất hiện với tên: `product.search`.
- Mở Attributes: `{"search.keyword": "Nước mắm", "search.has_filter": true, "search.result_count": 12}`.
- GIÁ TRỊ TỐI ƯU HÓA (SỰ LIÊN KẾT GIỮA METRICS VÀ TRACES):
  + Giả sử bảng Product có 1 triệu sản phẩm. Khi khách gõ "Nước mắm", thanh Trace `product.search` dài tới 3000ms (3 giây).
  + Đồng thời, bên Tab Metrics, chỉ số **Event Loop Lag** và **Total CPU Time** đột ngột dâng cao.
  + KẾT LUẬN NGAY TỨC KHẮC: Truy vấn tìm kiếm đang phải Full Table Scan (Quét toàn bộ bảng). Developer dựa vào bằng chứng này để viết thêm lệnh tạo Index (Đánh chỉ mục) trên cột Tên Sản Phẩm dưới MongoDB.

4. TỐI ƯU HÓA HỆ THỐNG GIÁM SÁT (CHỐNG NHIỄU - NOISE FILTERING)
-----------------------------------------------------------------
* BỐI CẢNH: Giao diện System Monitor được thiết lập tự động làm mới (Auto-refresh) mỗi 10 giây bằng cách gọi API `GET /api/telemetry/traces`. Tuy nhiên, bản thân hành động gọi API này cũng sẽ bị hệ thống Auto-Instrumentation "bắt" lại thành 1 Trace mới, tạo ra một vòng lặp vô tận khiến màn hình bị "spam" đầy rác.

* CÁCH GIẢI QUYẾT (CODE THỰC TẾ):
Tại file cấu hình `server/config/tracer.js`, chúng ta đã chủ động thiết lập bộ lọc (ignoreHook) để hệ thống nhắm mắt làm ngơ, không ghi nhận các URL dùng để giám sát:
```javascript
ignoreIncomingRequestHook: (req) => {
  const ignorePaths = ['/metrics', '/api/health', '/status', '/api/telemetry'];
  return ignorePaths.some((p) => req.url?.startsWith(p));
}
```
* Ý NGHĨA: Điều này thể hiện tư duy thiết kế hệ thống chuyên nghiệp (Production-ready). Việc giám sát không được phép tạo thêm gánh nặng hoặc sinh ra rác (noise) làm ảnh hưởng đến hiệu năng thực tế của phần mềm.

PHẦN 3: KỊCH BẢN DEMO HỆ THỐNG TRỰC TIẾP (QA TEST)
---------------------------------------------------------------
Để minh họa thực tế cho hội đồng đánh giá, dưới đây là kịch bản Demo trực tiếp sự hoạt động của Telemetry trên giao diện UI:

[BƯỚC 1: CHUẨN BỊ MÀN HÌNH GIÁM SÁT]
1. Đăng nhập hệ thống bằng tài khoản Quản lý (manager1).
2. Truy cập menu System Monitor (hoặc URL: /system-monitor).
3. Chuyển sang Tab "Traces" và để màn hình hiển thị chờ sẵn ở đó.

[BƯỚC 2: DEMO LUỒNG ĐĂNG NHẬP (auth.login) & CHỐNG HACK]
1. Mở một tab trình duyệt ẩn danh (Incognito), truy cập trang Đăng nhập (/signin).
2. Cố tình nhập sai tài khoản (VD: hacker / 123456) và bấm Đăng nhập.
3. Chuyển về màn hình System Monitor:
   - Sẽ xuất hiện ngay 1 Trace `auth.login` màu ĐỎ (báo lỗi).
   - Minh họa cho hội đồng: Hệ thống đã bắt được nỗ lực xâm nhập bất hợp pháp trong thời gian thực.

[BƯỚC 3: DEMO LUỒNG TÌM KIẾM (product.search) & THEO DÕI HÀNH VI]
1. Tại tab Ẩn danh, truy cập trang Khách hàng (/customer-portal).
2. Gõ từ khóa "Sữa" vào ô tìm kiếm.
3. Chuyển về màn hình System Monitor:
   - Xuất hiện Trace `product.search` màu XANH.
   - Mở chi tiết (Attributes) để show cho hội đồng thấy dòng: `{"search.keyword": "Sữa"}`. 
   - Minh họa cho hội đồng: Hệ thống thấu hiểu hành vi tìm kiếm của khách hàng (Search Insight) mà không cần phải truy vấn vào Database.

[BƯỚC 4: DEMO LUỒNG THANH TOÁN (order.checkout) & CHỐNG BÁN ÂM KHO]
1. Tại màn hình Customer, thêm vài món đồ vào giỏ hàng. Nhớ tổng số tiền.
2. Bấm "Thanh toán".
3. Chuyển về màn hình System Monitor:
   - Xuất hiện Trace `order.checkout` màu XANH.
   - Mở Attributes để show: `{"order.total_amount": [Tổng tiền]}`.
   - Trình bày điểm nhấn kiến trúc (QUAN TRỌNG): Giải thích với hội đồng rằng thời gian của Trace này chạy lâu hơn một chút vì hệ thống đang thực thi lệnh Atomic Update (`$inc` và `$gte`) khóa cứng dòng dữ liệu tại tầng MongoDB. Điều này triệt tiêu hoàn toàn Race Condition, đảm bảo 100 người mua cùng lúc vẫn không bao giờ xảy ra lỗi bán âm kho.

TỔNG KẾT BÁO CÁO
---------------------------------------------------------------
Hệ thống không chỉ đáp ứng hoàn chỉnh các chức năng nghiệp vụ (Use Cases) mà còn được thiết kế với tư duy của một hệ thống Enterprise (Doanh nghiệp lớn). Sự kết hợp giữa mã nguồn xử lý triệt để bài toán khó (Atomic Update chống bán âm kho) và bộ công cụ Observability trực quan đã giúp biến một phần mềm "hộp đen" thành một hệ thống minh bạch, an toàn, dễ giám sát và có thể mở rộng mạnh mẽ trong tương lai.
